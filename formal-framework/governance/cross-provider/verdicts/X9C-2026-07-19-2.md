## New and residual inconsistencies, severity-ranked

### BLOCKING 1 -- the literal HG1 instruction does not identify the v4.1 object required by A2

The operative header says v4.1. A2 requires a lead request containing
gate-id, action, canonical object path, digest, version, and scope, followed
by a reply echoing the gate ID, action, and digest suffix. The Gate Standard
lists only gate-id/action/digest/version, and HG1 instructs the lead to serve
`{HG1, ratify, <digest>, v4}`. The final Verdict block likewise calls the
object v4. Following the literal HG1 procedure would therefore name the
superseded version and omit required A2 fields. HG1 should not be served from
internally inconsistent gate text.

Locations: charter header/status; A2; Gate Standard; HG1; final Verdict.

### BLOCKING 2 -- the required structural-schema leg is not implemented as stated

S1-S3 and G2 require structural rejection of images, content-carrying links,
embedded structures, invalid type fields, alternate streams, and reparse
points. `_m5_schema` checks only NUL, UTF-8 decode, a `data:...;base64`
pattern, and a long base64-like token. New fixture A passed a remote Markdown
image, an HTML element, and a Type-B file lacking required fields. G7's honest
human-review assignment covers substantive reading judgments; it does not
remove the expressly mechanical S1 structural controls. Entry into force
cannot rely on a G2 leg that reports PASS for its named nonconformities.

Locations: charter S1-S3, G2 M5-SCHEMA, G4; guard `_m5_schema`
(`scripts/coherence_guard.py:128-144`) and artifact loop (`225-240`).

### MAJOR 1 -- structured registry form loses the governing gate type

`M5_REG_LINE` parses a gate ID, but `_m5_registry_bindings` returns only a
`filename -> digest` dictionary. `_m5_digest` and `_m5_pin` therefore accept
the right digest under the wrong gate type and do not validate action,
version, scope, canonical path, digest echo, or the HG2-R dependency set.
New fixture B mechanically passed HG4 for the charter and HG1 for a reading.
A5 correctly prevents that PASS from becoming operator authenticity, but G2
still promises comparison to the governing gate, not merely any structured
claim.

Locations: A2-A5, HG1/HG2/HG2-R, G2 M5-DIGEST; guard
`M5_REG_LINE` and `_m5_registry_bindings` (`147-161`), `_m5_digest`
(`163-170`), `_m5_pin` (`173-193`).

### MAJOR 2 -- point-in-time honesty is contradicted by remaining per-event scanner claims

G1 accurately limits the program to a scan when run and imposes two manual
service points. The Gate Standard and G2 nevertheless state that the guard
recomputes on every access, mutation, commit, and export. Nothing in the
supplied guard can observe those events. Either the remaining per-event claims
must be downgraded to the exact operator-run duty, or an independently pinned
event integration must be supplied and reviewed.

Locations: Gate Standard; G1; G2 M5-DIGEST; guard `main` and
`check_interpretation_layer`.

### MAJOR 3 -- source dependency and state-transition guarantees remain declarative

P1 promises automatic dependent suspension on source change, while G2/section
9 say M5-STATE enforces the state machine, read-only status, disabled use, and
disabled egress. The code checks a current state token, permitted filenames,
file digests, a guard pin, and one charter binding. It does not resolve P1
pointers, compare dependency sets, observe source changes, validate a prior
state, or enforce read/use/egress properties. v4.1 honestly reassigns part of
this to operator duties, but the contrary mechanical claims remain.

Locations: P1; G2 M5-STATE; section 9 states/transitions/preservation; guard
`_m5_state`, `_m5_pin`, and `check_interpretation_layer`.

### MINOR 1 -- implementation/version labels remain stale

The current script prints `coherence_guard v1` while the queue and amendment
record identify v1.2 behavior, and the gate-pointer registry header still
names charter v4. These labels do not create authority, but they make evidence
capture needlessly ambiguous during the HG1 transition.
